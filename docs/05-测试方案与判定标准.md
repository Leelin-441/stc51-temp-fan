## 1. 测试分层

本项目把验证拆成三层，三层各管一段，任何一层都不能替代另一层。

| 层次 | 名称 | 手段 | 能覆盖什么 | 覆盖不了什么 | 当前状态 |
| --- | --- | --- | --- | --- | --- |
| **L1** | 逻辑层 | PC 端 Python 等价仿真（把状态机、阶梯回差、报警保持、故障计数在 PC 上重写一遍并与固件的判定表逐条对拍） | 状态机的**判定逻辑与阈值**：所有档位切换边界、回差方向、报警进入/解除条件、故障计数 | 真实的 C 代码、C51 编译器行为、中断/时序、串口帧的**实际字节** | **待做**（Python 仿真尚未编写） |
| **L2** | 协议层 | `tools/serial_test.ps1`：`SIM T=` 注入确定温度 → 读回 `$S,` 帧 → 自动比对 ST 与 LEVEL | 串口协议字段顺序与含义、命令解析、定点数换算、状态名上报、**同样的输入是否每次都得同样的输出** | 真实传感器读数、电机是否真转、PWM 波形、发热、电源跌落 | **待执行**（脚本已就绪，需接板子跑） |
| **L3** | 物理层 | 真实升温激励（手握、热风、冰袋）+ 人工观察数码管 / 电机 / 蜂鸣器 / LED | 传感器通路、驱动电路、电机与 PWM 的**物理效果**、按键手感、整机在真实温度下是否可用 | 精确的数值复现（环境温度、风速、握持力度每次都不一样） | **待执行**（人工，需实物） |

### 1.1 为什么 L2 是必须做的，不能只靠 L3

这是本测试方案的核心论点：

1. **物理升温无法复现相同的数值。**
   用握持、电吹风或冰袋把 DS18B20 加热到"恰好 355（35.5℃）"，下一次最多只能做到"大约 35℃"。
   而阶梯回差的门限是 `Tset-20 = 330`、`Tset = 350`、`Tset+30 = 380`，门限之间只差 20 个定点数（2.0℃）。
   实际温度和门限处在同一量级、同一抖动范围内，**无法稳定地落在门限的哪一侧**。
   于是 L3 永远写不出"同样的条件下重复 3 次全部通过"这种结论 —— 只能说"当时看起来是对的"。

2. **L2 用 SIM 注入把温度变成确定值。**
   `SIM T=34.5` 进去，板上内部温度就是 345，一点不差。此时门限两侧可以精确取值：
   325 与 330、345 与 330、360 与 330，每次都是同一个数。
   这才让"重复 N 轮、全部通过"成为一句**可验证**的结论，而不是一句感觉。

3. **L2 是唯一能把"边界的哪一侧"测清楚的手段。**
   回差（迟滞）的本质是"同一条温度线上有两个不同门限"。要验证它，必须能在门限的**两侧各放一个确定的点**。
   L3 做不到这件事，L1 只能验证"我们对逻辑的理解"，只有 L2 能验证"**固件里真正烧进去的那份代码**在边界上是什么行为"。

4. **L2 可回归。** 代码改一行，重跑一条命令（约 3 分钟）就能知道有没有把别的东西改坏；L3 每次都要重新接线、重新加热、重新用眼睛看。

**结论：L2 不是"锦上添花的自动化"，它是本项目唯一能给出可复现判定的测试层。**

## 2. 为什么 8051 比 STM32 更需要 L2

| 对比项 | STM32 | STC89C52RC（本项目） |
| --- | --- | --- |
| 在线调试 | SWD/JTAG：可下断点、单步、实时看变量与寄存器 | **没有**。8051 传统内核没有 SWD/JTAG，Keil 的软件仿真也不是真实硬件 |
| 观测手段 | 调试器 + 串口 + 逻辑分析仪，多通道互相对照 | **基本只有串口**。LED/数码管/蜂鸣器只能表达极少的信息 |
| 缺陷定位 | 打断点看那一刻的变量，定位成本低 | 只能在代码里"打串口打印"，靠日志回推；改一次要重新编译烧录一次 |
| 运行时可干预性 | 可在线改内存、强制改变量 | 不能。只能通过**预先留好的命令**（本项目就是 `SIM` / `SET` / `MODE` / `LEVEL` / `RESET`）间接干预 |

因为 8051 既不能单步、也不能在线改变量，**串口是唯一的信息出口**。
这个唯一出口一旦不可靠（字段顺序错了、定点数没换算、状态名拼错），整个项目的可观测性就归零 —— 你连"到底哪里错了"都不知道。

所以对 51 来说，"把串口协议做成可自动回归的测试"不是优化项，而是**唯一的调试基础设施**。
`tools/serial_test.ps1` 就是把这条唯一通道变成自动化回归的工具。

## 3. 环境与接线

### 3.1 硬件清单

| 物品 | 说明 |
| --- | --- |
| 开发板 | 普中 / 清翔 HC6800-ES 系列，STC89C52RC，**晶振 11.0592MHz**（见 `config.h` 第 1 节） |
| USB 转 TTL 模块 | CH340 / CP2102 / FT232 均可，需先装好驱动 |
| 杜邦线 | 3 根：TXD、RXD、GND |
| 温度激励 | 手（约 30~35℃）、电吹风（可到 60℃+）、冰袋 / 酒精棉（降温） |
| （可选）示波器 | 测 P1.0 的 PWM 波形，L2 覆盖不到，见第 10 节 |

### 3.2 接线表（USB 转 TTL ↔ 开发板）

| USB 转 TTL 引脚 | 开发板引脚 | 说明 |
| --- | --- | --- |
| TXD | **P3.0（RXD）** | 交叉：模块发 → 单片机收 |
| RXD | **P3.1（TXD）** | 交叉：单片机发 → 模块收 |
| GND | **GND** | 必须共地。不共地一定收不到数据 |
| VCC / 3V3 / 5V | **★ 不要接！** | 开发板自己由 USB/DC 供电，两个电源打架会烧模块或烧板子 |

> ★ 接线三大坑：
> 1. **不要接 VCC** —— 板上已有电源，两个电源并联会互相灌电流。
> 2. **TXD/RXD 必须交叉** —— 接成 TXD-TXD 的表现是"一帧都收不到"，不是"时好时坏"。遇到完全收不到数据，第一个怀疑对象就是这里。
> 3. **`config.h` 特意把按键放在 K3(P3.2)/K4(P3.3)**，把 P3.0/P3.1 完整留给串口 —— 所以串口测试和按键操作**可以同时进行**，不用拔线。

### 3.3 串口参数

| 参数 | 值 | 说明 |
| --- | --- | --- |
| 波特率 | **9600** | 11.0592MHz 晶振下误差为 **0** |
| 数据位 | 8 | |
| 校验位 | None | |
| 停止位 | 1 | |
| 流控 | None | 脚本里显式设为 `Handshake.None`、`DtrEnable=false`、`RtsEnable=false` |

> ⚠️ **不是 115200。** 一个常见的错误是"顺手写成 115200"。
> 本项目固定 9600，原因写在 `config.h` 第 1 节：11.0592MHz 是为了让波特率整除，此时 9600 的误差为 0。
> 如果你把上位机设成别的波特率，表现是收到大量乱码字符而不是干净的 `$S,` 行。

### 3.4 帧格式表（`config.h` 第 5 节，10 个数据字段）

**板卡 → 上位机（每 1s 一帧，状态变化时立即补发）：**

```
$S,<ms>,<T>,<SET>,<LEVEL>,<DUTY>,<ST>,<MODE>,<BUZ>,<SIM>,<SENSOR>
```

官方示例：`$S,12345,355,350,2,66,MID,AUTO,0,0,OK`

| # | 字段 | 含义 | 取值 / 示例 | 易错点 |
| --- | --- | --- | --- | --- |
| 0 | `$S` | 帧头 | 固定 `$S` | 用 `StartsWith('$S,')` 判断，别用 `-match` 松散匹配 |
| 1 | `ms` | 上电以来的毫秒数 | `12345` | 用来判断板子中途是否复位（时间戳突然变小） |
| 2 | `T` | 当前温度 | `355` | **★ 定点数 ×10**：355 = 35.5℃，不是 355℃ |
| 3 | `SET` | 目标温度 | `350` | **★ 同样是 ×10 定点数**：350 = 35.0℃；范围 200~600 |
| 4 | `LEVEL` | 档位 | `0` / `1` / `2` / `3` | 0=停机 1=低速 2=中速 3=全速 |
| 5 | `DUTY` | PWM 占空比**百分数** | `0` / `34` / `66` / `100` | 不是 PWM 级数。级数是 0/17/33/50（分母 50），换算成百分数是 0/34/66/100 |
| 6 | `ST` | 状态名 | `STOP` `LOW` `MID` `HIGH` `ALARM` `FAULT` `MANUAL` | 大小写必须完全一致 |
| 7 | `MODE` | 模式 | `AUTO` / `MANUAL` | |
| 8 | `BUZ` | 蜂鸣器瞬时状态 | `0` / `1` | 报警时是断续的，抓帧时可能抓到 0 也可能抓到 1，**不要拿它做判定依据** |
| 9 | `SIM` | 是否处于仿真模式 | `0` / `1` | 跑 L2 时应该是 1（除 R5-01 外） |
| 10 | `SENSOR` | 最近一次 DS18B20 读取结果 | `OK` / `NOPRESENT` / `BADCRC` / `NOINIT` | 仿真模式下无意义；R5-01 拔线后期望 `NOPRESENT` |

> ### ★★★ 最大的坑：温度是 ×10 定点数
>
> **命令用摄氏度，帧用定点数，两边不是同一个数量级：**
>
> | 方向 | 写法 | 数值 |
> | --- | --- | --- |
> | 上位机 → 板卡 | `SIM T=42.5` | 摄氏度，**带小数点** |
> | 板卡 → 上位机 | `T=425` | 定点数，**不带小数点** |
>
> 于是"35.0℃"在期望值里必须写成 **350**。
> 新手最常见的错误是看到帧里 `T=355` 就以为板子在报 355℃，然后去怀疑传感器坏了。
> 另一个错误是把期望值写成 `35`，于是任何温度都不匹配。
> 本脚本的用例表里**所有期望值一律是帧里的定点数**（例如 `SET = 250` 表示 25.0℃）。

### 3.5 控制参数速查（判定用，全部来自 `config.h` 第 3 节）

设目标温度 $T_{set}$（默认 350 = 35.0℃，可调 200~600），温度 $T$ 均为定点数：

| 条件 | 动作 |
| --- | --- |
| $T \ge T_{set} - 20$ | 进低速（LEVEL 1） |
| $T \le T_{set} - 40$ | 回停机（LEVEL 0） |
| $T \ge T_{set}$ | 进中速（LEVEL 2） |
| $T \le T_{set} - 20$ | 回低速（LEVEL 1） |
| $T \ge T_{set} + 30$ | 进全速（LEVEL 3） |
| $T \le T_{set} + 10$ | 回中速（LEVEL 2） |
| $T \ge T_{set} + 80$ | 报警 |
| $T \le T_{set} + 40$ 且持续 **5000ms** | 解除报警 |
| DS18B20 连续 **3** 次读失败 | 判传感器故障（FAULT，停机） |

默认 $T_{set}=350$ 时的具体数值：

| 事件 | 门限（定点数） | 门限（℃） |
| --- | --- | --- |
| 回停机 | ≤ 310 | 31.0 |
| 进低速 | ≥ 330 | 33.0 |
| 进中速 | ≥ 350 | 35.0 |
| 进全速 | ≥ 380 | 38.0 |
| 报警 | ≥ 430 | 43.0 |
| 报警解除 | ≤ 390 | 39.0 |

### 4.1 R4-02 的时序计算（为什么必须把 ReadMs 压短）

这是全部用例里唯一一条**对时间敏感**的用例，必须算清楚：

| 时刻（t≈） | 事件 | 说明 |
| --- | --- | --- |
| 0 | 脚本开始本条用例 | — |
| 0.4s | `RESET` 后的等待结束 | 清报警、$T_{set}$ 回 350 |
| 0.6s | `MODE AUTO` 后等待结束 | — |
| 0.6s | `SIM T=44.0` 下发 | 440 ≥ 430 → **报警成立**，状态变化立即补发一帧，之后每 1s 一帧 |
| 1.8s | `SIM T=35.0` 下发 | 350 ≤ $T_{set}+40$=390 → **解除条件从此刻起成立** |
| 2.0s | `STATUS` 下发 | 强制立即回一帧（此时仍是 ALARM） |
| **2.1s** | **读取窗口开始**（ReadMs=1200） | — |
| **3.3s** | **读取窗口结束**，取窗口内最后一帧做判定 | 最后一帧大约产生在 3.3s |

**报警最早可能在什么时候解除？** 取两种口径中更严的那个：

- 口径 A（"解除条件须持续满 5000ms"）：$1.8 + 5.0 = \mathbf{6.8s}$
- 口径 B（"报警至少维持 5000ms"）：$0.6 + 5.0 = 5.6s$

无论按哪种口径，**最早的解除时刻都不早于 5.6s**，而读取窗口的右端是 **3.3s**，
距离最严口径（6.8s）还有约 **3.5s 余量** —— 窗口内取到的任何一帧都必然仍是 `ALARM`。

**为什么 ReadMs 必须压到 1200ms：**
若沿用默认 2500ms（窗口到 4.6s）还勉强安全，但只要稍加额外等待（例如 `ExtraWaitMs` 给了 3000ms），
窗口右端就会越过 6.8s，此时取到的"最后一帧"**恰好是报警已经解除之后的帧**，
合格的固件反而会被判成失败。所以本用例显式写死 `ReadMs = 1200`，
把观测点钉在"报警成立之后、解除之前"的窗口正中。

> 反向验证：把 ReadMs 改成 6000ms 后本条**必然失败**。这是一个很好的"测试脚本自身是否可信"的负向验证，
> 建议在对板子做第一次正式回归前先用它确认脚本确实能抓到失败。

### 4.2 用例编号与 L1 仿真的对应

L2 的用例编号（R1-01 … R6-01）与 L1 逻辑层仿真的编号**必须逐一对应**，
这样同一个编号在两层之间可以互相印证：L1 说"逻辑应该这样"，L2 说"固件实际这样"。
如果两层对同一条用例给出不同结论，说明**至少有一层的理解是错的**，必须先查清楚再继续。

> 这类问题 L1/L2 **永远发现不了**。

## 6. 判定标准

### 6.1 L2 判定：通过 / 失败

| 判定 | 条件 |
| --- | --- |
| ✅ **通过** | 该用例期望的 **ST 状态名完全一致**（大小写敏感、逐字符相等）**且 LEVEL 数值一致**；若该用例声明了 `SET` 期望，`SET` 也必须一致；且读取窗口内**能收到至少一帧** |
| ❌ **失败** | 上述任意一项不满足；或读取窗口内**一帧都没收到**（脚本记为"读取窗口内没有收到 `$S,` 帧"，**不抛异常、不中断整轮**） |
| ⏭ **跳过** | 用例表本身的 `Cmds` 与 `Delays` 条数不一致（配置错误），脚本打印红色错误并跳过该条 |

**逐条判定要素（三者必须同时成立）：**

1. **状态名一致**：`ST` 字段逐字符相等（`STOP` ≠ `stop`）。
2. **档位一致**：`LEVEL` 数值相等。
3. **期间无复位**：该用例执行前后，帧里的 `ms` 字段必须**单调不减**。
   若 `ms` 突然从小变大（例如从 45000 跳回 800），说明板子中途复位过 —— 即使这一帧的 ST/LEVEL 恰好正确，**本条也必须判为无效**。
   > 这一条目前需要人工核对 CSV 里的 `实收帧`（脚本已把整帧原文记进 CSV）。
   > 后续可把"ms 单调性检查"加进脚本做成自动判定，属于**已知的待改进项**。

### 6.2 部分通过（可以接受但不合格）

出现下列情况时记为"部分通过"，**不能算通过**，必须写清楚现象：

| 现象 | 含义 | 处理 |
| --- | --- | --- |
| ST 对、LEVEL 对，但 `DUTY` 与档位不匹配（例如 LEVEL=3 却 `DUTY=34`） | 状态机对了，PWM 输出没跟上 | 记为部分通过，查 PWM 映射表 |
| ST/LEVEL 对，但 `MODE`、`SIM`、`SENSOR` 字段异常 | 协议次要字段有问题 | 记为部分通过，单独记录 |
| 判定的那一帧正确，但**期间出现过错误帧**（最后一帧对，前面有错的） | 存在间歇性缺陷 | 记为部分通过（脚本只取最后一帧，天然会漏掉这种） |
| `LEVEL` 对但**电机实际不转**（L3 才能发现） | 驱动电路问题 | L2 通过、L3 失败 —— 这正是必须做 L3 的原因 |

### 6.3 整体验收门槛

| 层次 | 门槛 |
| --- | --- |
| L1 | 全部编号与 L2 用例一一对应，逐条给出逻辑期望值，**无对不上的条目** |
| L2 | 连续 **3 轮**全部 14 条通过（通过率 100%），且第 8 节记录表中有对应的执行记录 |
| L3 | L3-01 ~ L3-12 **全部 12 项**观察到预期现象；任何一项"电机不动作"或"不报警"都视为整机不合格 |
| 稳定性 | 连续运行 1 小时无复位、无死机（见第 9 节） |

> **三层全绿才算项目通过。** L2 100% 通过但 L3 电机不转，项目就是不合格的。

## 9. 稳定性测试（连续运行 1 小时）

## 10. 已知的测试盲区

诚实列出**本轮测试覆盖不到的东西**。这些不是"顺便提一句"，而是必须在实机验收时单独确认的风险项。

| 盲区 | 为什么 L1/L2 覆盖不到 | 需要什么手段 | 风险等级 |
| --- | --- | --- | --- |
| **电机实际转速** | 串口只能报 `LEVEL` 和 `DUTY` 这两个**软件侧数字**。软件说"100% 占空比"和电机真的转得快，是两件事 | 转速计 / 手机慢动作录像 / 贴纸+光电计数 | 高 |
| **PWM 波形质量** | 帧里的 `DUTY` 是软件算出来的数，不代表 P1.0 引脚上真有 100Hz、100% 的方波。定时器配置错误、中断被长时间占用都会让波形变形 | **示波器**测 P1.0（`PWM_LEVELS=50`、`PWM_ISR_US=200` → 周期应为 10ms，即 100Hz） | 高 |
| **电机驱动发热** | ULN2003 和板载三极管的热是物理量，串口看不到；长时间中速运行可能烫到损坏 | 手指触摸 / 红外测温 / 热成像；连续运行 1 小时后测 | 中高 |
| **电源跌落与复位** | 电机启动瞬间的浪涌可能把 5V 拉低导致单片机复位。串口的 `ms` 字段能发现复位，但**发现不了"为什么复位"** | 示波器测 VCC 纹波；对比电机启动瞬间的电压跌落 | 高 |
| **DS18B20 的实际读数准确性** | L2 用的是 `SIM` 注入的假温度，**根本没经过传感器**；L3 也无法给出精确到 0.1℃ 的参考值 | 与标准温度计对比；冰水混合物（0℃）、沸水（约 100℃）做两点校准 | 高 |
| **单总线时序余量** | 4.7k 上拉是否够、长导线是否导致时序失败，取决于布线和线长 | 加长杜邦线到 50cm/1m 复测；示波器看 DQ 波形 | 中 |
| **按键手感与寿命** | 消抖逻辑可以靠代码审查，但机械触点的实际抖动、手感只能手测 | 人工连按数百次 | 低 |
| **数码管显示内容** | L2 完全不看数码管（串口和数码管是两条独立通路，可能一个对一个错） | L3 人工逐位核对显示值与串口 `T`/`SET` | 中 |
| **蜂鸣器实际音调/音量** | 帧里的 `BUZ` 只是"当前是否在响"的瞬时值，且报警时是断续的，抓帧可能抓到 0 也可能抓到 1 | L3 用耳朵听节奏；**不要把 `BUZ` 当判定依据** | 低 |
| **EEPROM / 掉电保存** | 本工程未使用 EEPROM，"重启后参数是否保持"只能实机验证 | E-15 手工测试 | 低 |
| **长时间运行的偶发缺陷** | 3 轮 L2（约 3 分钟）跑不出偶发问题；间歇性缺陷在"取最后一帧"的判定方式下也可能被掩盖 | 第 9 节 1 小时稳定性测试 + 保留完整串口日志回放 | 中 |
| **C51 编译器的实现细节** | L1 是 Python 等价仿真，验证的是"我们对逻辑的理解"，不是 Keil C51 编译出来的真实机器码；整型提升、`sbit` 读写、中断重入等都可能与仿真不同 | 只有 L2/L3（跑真实固件）能覆盖 | 中 |
