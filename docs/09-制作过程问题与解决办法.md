## 问题 1：DS18B20 一直读到 85.0℃

**现象**
第一次写测温程序，串口帧里 `T` 字段永远是 `850`（即 85.0℃），数码管也一直显示 `85.0`，把传感器放在空调出风口、用手捂、用热风吹，读数**一点都不动**。一开始还以为是传感器坏了，换了两个新的 DS18B20，还是 85.0℃。

**排查过程**
1. 先用示波器（后来退一步用串口打印中间量）确认 1-Wire 复位脉冲有没有器件应答：回答是**有应答**——说明 DS18B20 在总线上，接线没断，器件活着。
2. 再打印原始的两字节暂存器数据：发现读回来的就是 `0x0550`，也就是 **85℃**，不是我的换算代码算错。
3. 查 DS18B20 数据手册：**85℃ 是它的 Power-on Reset 默认值**，即上电后温度寄存器里的初始内容。**只有当一次温度转换真正完成，寄存器才会被写入真实值。**
4. 回头看我当时的代码：

```c
/* 错误的早期版本 —— 发起转换后立刻就读 */
ds_start_convert();
ds_read_scratchpad(&raw);      /* 错误！这里距上一条只有几十微秒 */
```

只有发起转换，**没有等待**，读回来的必然是还没被覆盖的上电默认值 85℃。

**根本原因**
DS18B20 的 12 位温度转换是在**芯片内部**完成的，主机发起命令后必须给它时间。12 位分辨率下最大转换时间是 **750ms**。我在发起转换后立刻读暂存器，读到的是上电默认值，不是本次转换结果。**85.0℃ 这个数字本身就是一个信号：它不代表"很热"，它代表"这次读的不是真实温度"。**

**解决办法**
1. 发起转换后**必须等待 ≥750ms**，我在 `config.h` 里定义 `DS_CONV_MS 800`（750ms + 余量）。
2. 等待期间**不用死延时**，改成状态机/时间片：发起转换时记下时间戳，主循环里到了时间再去读暂存器。PWM 和数码管扫描都在定时器中断里跑，不受影响。
3. 顺手加了一个**健全性判断**：如果读回来的值恰好是 850（85.0℃）且随后没有变化，就在 `SENSOR` 字段报异常，而不是傻乎乎地把它当真实温度去控制电机。

**经验总结**
传感器给你一个"看起来很合理但永远不变"的数字时，先怀疑**流程**，不要先怀疑硬件。85.0℃ 是 DS18B20 的"我还没准备好"，我后来把它当成一个诊断标志——**看到 85.0 就去查转换时序，而不是去查接线**。

## 问题 2：DS18B20 读到 0 或乱码

**现象**
换成洞洞板自己焊的转接小板之后，读数变成 `0.0`，或者在不同温度之间乱蹦（`12.5` → `67.0` → `0.0`）。有时候程序启动后前几秒读数是好的，一碰线就跳到 0。

**排查过程**
1. 先怀疑代码：因为同一份代码在开发板自带的 DS18B20 座上完全正常，所以**代码逻辑没问题**，问题出在接线。
2. 量 DQ 到 +5V 之间的电阻：断开了——**上拉电阻没接**。
3. 补上一个 4.7k 之后好转，但还有偶发跳变。再查：我把上拉电阻的另一端接到了板子的 **3.3V** 上（板上有个 3.3V 输出排针，顺手就插了）。
4. 换成 **+5V** 后稳定很多。又发现我用了一根 **30cm 的杜邦线**把 DQ 引出到板外，线一长，边沿变缓，读时隙采样点容易采错。

**根本原因**
DS18B20 的 DQ 是**开漏/准双向**结构，自己不能输出高电平，**必须靠外部上拉电阻把总线拉高**，这是 1-Wire 总线空闲态的基础。三个具体错误：
- **没接 4.7k 上拉**：总线无法回到高，主机释放总线后读数全是 0（或随机）；
- **上拉到 3.3V**：DS18B20 由 5V 供电时，其输入高电平门限是 0.7×VDD = 3.5V，3.3V 刚好够不着门限，形成临界状态，时好时坏；
- **杜邦线太长**：线容加大，上拉电阻的 RC 上升时间变长，而我的读时隙采样点在拉低后约 11µs，边沿还没建立起来就采样了。

**解决办法**
1. **强制 4.7k 上拉，另一端接 +5V**，和 DS18B20 的 VDD 同源。这一点直接写进接线文档的必检项。
2. DQ 走线尽量短（10cm 以内），不做"引到桌面另一头"的操作。
3. 读时隙采样点不要贴边沿，固定在**拉低后约 11µs** 的中段位置，给边沿建立留余量（这条和问题 15 是同一个根）。
4. 把 `SENSOR` 字段的 `NOPRESENT` / `BADCRC` 用起来：即使偶发失败也能在串口帧里看到，不用猜。

**经验总结**
1-Wire 这种"一根线供电＋通信"的总线，**上拉电阻不是可选件，是电路的一半**。而且**上拉到几伏很关键**——3.3V 拉 5V 器件是我花时间最多的一次弯路，因为它"有时能工作"，最难查。

## 问题 3：电机不转，但程序显示占空比已经是 100%

**现象**
串口帧里 `DUTY` 字段明明是 `100`，`LEVEL=3`，状态 `HIGH`，`P1.0` 用万用表量也确实是高电平——**但电机就是不转**，一点动静都没有。换了个电机也不转。

**排查过程**
1. 确认软件：量 P1.0 → 高电平（3.5V 左右），`DUTY=100`，软件侧完全正常。
2. 量 ULN2003 的对应输出脚 OUT1：在 P1.0 为高时，OUT1 对地电压 ≈ **0.1~0.3V**，说明达林顿管**确实导通了**，ULN2003 工作正常。
3. 量电机两端电压：**0V**。这就说明问题不在驱动，在负载接法。
4. 我当时的接法是：电机的一端接 **GND**，另一端接 ULN2003 的 **OUT1**。改成：电机一端接 **+5V**，另一端接 **OUT1** → 立刻转起来。

**根本原因**
**ULN2003 是低边（灌电流）驱动器，不是高边驱动器。** 它的内部结构是"达林顿管 + 续流二极管"，集电极接负载、发射极接地：

- 输入 IN 为高 → 达林顿管导通 → **OUT 被拉到接近 0V（接地）**
- 此时电流路径是 **+5V → 负载 → OUT → GND**

所以负载必须接在 **+5V 和 OUT 之间**。我接成"GND 和 OUT 之间"，等于把负载接在了开关的两端——开关导通时两端都是 0V，负载上当然没有压降，电机不转。**"OUT 导通 = 接地"这个直觉没转过来，是低边驱动的经典坑。**

**解决办法**
1. 改接：**电机一端 → +5V，另一端 → ULN2003 OUT1**，问题立刻消失。
2. 在软件层面把这个极性**封装成宏**，避免以后再绕：

```c
sbit MOTOR = P1 ^ 0;
#define MOTOR_ON   1   /* ULN2003 反相：IN 高 → OUT 拉低 → 负载通电 */
#define MOTOR_OFF  0
```

上层只写 `MOTOR = MOTOR_ON`，**"高=通电"的直觉只在这三行里破例一次**，不在几百行 PWM 代码里到处写 `!`。
3. 画了一张接线图贴在实验台上，标注"低边驱动"四个字。

**经验总结**
用驱动芯片前先问三个问题：**它是高边还是低边？是反相还是同相？负载该接在哪两个点之间？** 这三个问题的答案必须写在代码注释里，因为它们不是软件能补救的错误——软件怎么调占空比都没用。

## 问题 4：电机一启动单片机就复位

**现象**
最开始的版本，电机**从不转**（问题 3）修好之后，变成更麻烦的：电机只要一转，数码管立刻黑一下、串口输出中断、程序从头开始（串口 `ms` 字段归零）。转速越高越容易复位，全速档几乎一动就复位。

**排查过程**
1. 先怀疑程序跑飞（看门狗/野指针）：把 PWM 中断里除了翻转 IO 之外的所有代码都删掉，还是复位 → **不是软件问题**。
2. 用示波器量板子的 5V 电源轨：电机启动瞬间，5V 轨从 5.0V **跌到 4.1V 左右**，有一个明显的尖峰跌落。**单片机的最低工作电压约 4.0V，这一跌直接踩线。**
3. 发现电机是从**开发板上的 5V 排针**取电的，而这个 5V 又是 USB 口供过来的（USB 限流 500mA 左右），电机启动电流几百 mA，一拉就掉。
4. 又发现电机两端**没有续流二极管**，关断瞬间的感生反电动势叠加在电源上，形成尖峰。

**根本原因**
两个原因叠加：
1. **电源共用且容量不足**：电机的启动浪涌电流在共享的 5V 轨上产生压降，把单片机一起拉进复位区。USB 供电的 5V 本来就是"弱电"，带不动电机这类感性负载。
2. **感性负载切换的反电动势**：电机是电感，PWM 关断时电流被强行切断会产生反向尖峰电压（几十伏级），既打电源又打驱动管。ULN2003 内部虽然自带有续流二极管，但**长引线带来的寄生电感**仍然会把尖峰耦合到电源上。

**解决办法**
四件事一起做，全部做完才彻底稳定：
1. **电机独立 5V 供电**：用一个单独的 5V 电源（或另一路 USB 电源）给电机供电，**不再从板载 5V 取电**。
2. **共地**：独立电源的 GND 与单片机板 GND 必须**接在一起**，否则 ULN2003 的控制信号没有参考电平，电机驱动会完全失效。
3. **并 470µF 电解电容**：在电机电源入口处并联 **470µF 电解电容**（再并一个 0.1µF 陶瓷电容滤高频），把浪涌电流从"直接从电源抽"变成"先从电容抽"，电压跌落从 0.9V 降到 0.2V 以内。
4. **电机两端反并联 1N4007 续流二极管**：阴极接 +5V、阳极接 OUT，给关断时的反向电流一条泄放回路。

改完后再量 5V 轨：波动小于 0.1V，电机全速、频繁启停都不再复位。

**经验总结**
**"电机和单片机共用 USB 5V"是嵌入式入门最典型的自杀式接法。** 判断方法很简单：**一启动大功率负载就复位/花屏，先量电源，别调代码。** 感性负载的供电要当成一个独立子系统来设计：独立电源 + 共地 + 大容量储能 + 续流回路，四件套缺一不可。

## 问题 5：电机转速"忽快忽慢"，噪声大

**现象**
功能全部跑通之后，我发现一个"功能正确但体验很差"的现象：温度稳定在 35.0℃ 附近时，电机转速**来回变**——一会儿中速、一会儿低速、偶尔还停一下再启动，听起来"呜呜呜"地一顿一顿，噪声明显比匀速大。

**排查过程**
1. 看串口日志（每 1s 一帧）：`LEVEL` 字段在 `1`、`2`、`0` 之间反复跳，`T` 字段在 `349`、`350`、`351`、`348` 之间小幅波动，`SET=350`。
2. 当时的判定逻辑是**单阈值**：

```c
/* 早期单阈值版本 —— 抖动源 */
if (T >= TSET)          level = LV_MID;
else if (T >= TSET - 20) level = LV_LOW;
else                     level = LV_STOP;
```

温度在 `350` 上下抖 2~3 个点（0.2~0.3℃，完全正常的热噪声），状态就跟着抖。
3. 数了一下 10 秒内的切换次数：**十几次**。也就是说电机在 10 秒里启停了十几次。

**根本原因**
**单阈值 + 慢变量 + 噪声 = 临界点振荡（chattering）。** 温度信号本身带噪声（DS18B20 的分辨率是 0.0625℃，但气流扰动带来的实际波动更大），当控制量恰好压在某一个阈值上时，任何微小扰动都会让判定结果翻转。对电机这种**机械执行机构**，每次翻转都是一次启停冲击：启动电流大、齿轮受力大、噪声大、寿命短。

**解决办法**
改成**四档阶梯回差（迟滞）**——每个档位用**两个不同的阈值**，进档阈值和退档阈值之间留一段死区。这样温度必须在同一个方向走够距离才能改变判定，小幅抖动被死区吞掉。

`config.h` 里的最终参数（单位 0.1℃，相对 Tset 的偏移）：

```c
#define LV_ENTER_LOW    (-20)   /* T ≥ Tset-2.0℃ 进低速 */
#define LV_EXIT_LOW     (-40)   /* T ≤ Tset-4.0℃ 回停机 */
#define LV_ENTER_MID    (  0)   /* T ≥ Tset      进中速 */
#define LV_EXIT_MID     (-20)   /* T ≤ Tset-2.0℃ 回低速 */
#define LV_ENTER_HIGH   ( 30)   /* T ≥ Tset+3.0℃ 进全速 */
#define LV_EXIT_HIGH    ( 10)   /* T ≤ Tset+1.0℃ 回中速 */
```

| 档位 | 进档 | 退档 | 死区 |
|---|---|---|---|
| LOW | T ≥ Tset−2.0℃ | T ≤ Tset−4.0℃ | **2.0℃** |
| MID | T ≥ Tset | T ≤ Tset−2.0℃ | **2.0℃** |
| HIGH | T ≥ Tset+3.0℃ | T ≤ Tset+1.0℃ | **2.0℃** |

报警也用了同样的思路：进 `T ≥ Tset+8.0℃`，出 `T ≤ Tset+4.0℃` 且保持 **5 秒**（`ALARM_HOLD_MS 5000`）。

改完后同样的 10 秒窗口：切换次数从十几次降到 **0~2 次**，电机声音明显变平稳。

**经验总结**
**只要被控量是"有噪声的模拟量"，而执行机构是"开关式"的，就一定要做回差。** 这不是可选的优化，而是必要条件。回差宽度的选法：**要大于噪声峰峰值，又要小于你愿意接受的温度控制误差**——我的噪声约 0.3℃，我把死区定在 2.0℃，两者留了足够余量，同时 2℃ 的温度误差对散热应用完全可接受。

## 问题 6：数码管显示重影 / 闪烁

**现象**
显示能出数字，但每个数字都像"糊了一层"——本该熄灭的段有淡淡的亮（重影），而且整体有可见的闪烁感，摄像头上看特别明显。快速变化的位（比如温度从 `34.9` 跳到 `35.0`）会拖一道影子。

**排查过程**
1. 先看代码，找到动态扫描部分：

```c
/* 早期版本 —— 没有消隐 */
for (i = 0; i < 8; i++) {
    SMG_A = i & 1; SMG_B = (i >> 1) & 1; SMG_C = (i >> 2) & 1;  /* 直接换位选 */
    SMG_SEG_PORT = seg_code[digit[i]];                          /* 直接换段选 */
    delay_ms(1);
}
```

2. 分析：**位选一换，段选还是上一位的数据**，于是上一位的段码被短暂地打在新位上，这就是重影的来源。
3. 再算刷新率：8 位 × 1ms = 8ms 一帧 → **125Hz**，理论上不闪。但实测有闪，说明主循环里还有其他耗时代码（DS18B20 的 800ms 等待、串口发送等）**把扫描节奏拖长了**，实际刷新率远低于 125Hz。

**根本原因**
两个独立问题：
1. **没有消隐**：切换位选和写段选之间有"新旧数据同时在线"的窗口，产生鬼影。
2. **扫描节奏被主循环拖累**：动态扫描的刷新率取决于扫描循环执行得多稳定。只要扫描在主循环里跑，任何长耗时操作都会破坏刷新率，导致闪烁。

**解决办法**
1. **先关段选再换位选**：在改位选之前，先往段选端口写 **0xFF**（共阳数码管全灭），把影子切断。顺序必须是"**消隐 → 换位 → 写新段码**"，不能反过来。
2. **把扫描搬进定时器中断**：让扫描完全独立于主循环。我现在 `TICK_MS 100` 是状态机周期，显示用 `OLED_MS 200` 刷新数据，**但扫描本身在定时器中断里以固定 2ms/位 的节奏跑**——8 位 × 2ms = 16ms 一帧，也就是 **62.5Hz**，无可见闪烁，而且不受主循环影响。
3. 位选用的是 74HC138（P2.2/P2.3/P2.4 三人组成 3-8 译码），换位就是改这三个 IO，比端口全写更省事，也要一起放在消隐之后。

**经验总结**
**动态扫描必须放进定时器中断，不能放主循环**——这是数码管显示的第一原则。只要它还挂在主循环里，你后面每加一个功能都可能让它闪。消隐的顺序也要背下来：**消隐 → 换位 → 写段**，反过来必出鬼影。

## 问题 7：数码管位序反了（第 0 位显示在最右边）

**现象**
自检程序里我写的是"从第 0 位开始依次点亮"，预期是**从左往右**或至少从板子丝印的 0 号位开始。实际现象是：我点"第 0 位"，亮的是**最右边**那一位；点"第 7 位"，亮的是最左边。整体顺序**完全颠倒**。

**排查过程**
1. 先确认不是软件循环写反了：把循环打印出来看，i 从 0 到 7，送进 `SMG_A/B/C` 的是 `i` 的低三位，逻辑没错。
2. 单独测：给 `A=0, B=0, C=0`（即 74HC138 的 Y0 输出有效），看哪一位亮 → 亮的是**最右**。
3. 查普中 HC6800-ES 的原理图，发现 74HC138 的 A/B/C 与位号的连接**不是**我假设的"A 接最低位"。不同批次的板子走线不同：有的把 **C 接最低位**，有的把 A 接最低位。我手上这块属于前者。

**根本原因**
这纯粹是**硬件连线约定与软件假设不一致**的问题。74HC138 是 3-8 译码器，输入 `ABC` 的组合决定哪个输出有效，但 **"ABC 谁是低位"由 PCB 走线决定，不是由芯片决定**。我在软件里默认"`A` 是最低位"，板子实际是"C 是最低位"，两者恰好反序，于是位号整体倒过来。

**解决办法**
不要硬编码，**做成一个配置宏**，一行切换：

```c
/* 74HC138 的 A/B/C 与位号的对应关系。
   0 = A 接最低位（普中默认）
   1 = 反过来（有些板子把 C 接最低位）
   如果自检程序点亮的位号和预期相反，把这里改成 1。 */
#define SMG_BIT_REVERSE 0
```

软件里送位号时统一走一个转换函数：

```c
/* 位号 → 74HC138 的 A/B/C */
static void smg_select_bit(u8 bit)
{
#if SMG_BIT_REVERSE
    bit = (u8)(SMG_DIGITS - 1 - bit);   /* 整体倒序 */
#endif
    SMG_A = bit & 0x01;
    SMG_B = (bit >> 1) & 0x01;
    SMG_C = (bit >> 2) & 0x01;
}
```

换板子只改 `SMG_BIT_REVERSE` 这一个数字，**不在显示代码里到处改位号**。

**经验总结**
凡是"硬件决定了顺序、软件要知道顺序"的地方，**都做成配置项，不要写死在逻辑里**。这个习惯后来扩展到整个工程：所有引脚和参数集中在 `config.h`，换板子只改一个文件。位序反转这件事本身很小，但它是我第一次意识到"**配置与逻辑分离**"的价值。

## 问题 8：数码管只亮一位或全亮不灭

**现象**
两种相反的症状都遇到过：
- **只亮一位**：不管程序怎么循环，始终只有某一位亮，其他七位不亮；
- **全亮不灭**：8 位同时亮着，显示的是 8 个数字叠在一起的一团，完全没有动态扫描的效果。

**排查过程**
1. 先量 74HC138 的三个输入脚 P2.2 / P2.3 / P2.4 的电压，手动改变这三个脚的电平，看输出位是否跟随变化 → 发现**有一个脚的电平不变**。
2. 顺线查：原来我的杜邦线插错了一根——本该插在 P2.2/P2.3/P2.4 上，实际有一根插到了旁边的 P2.5。这就解释了"只亮一位"：A/B/C 有一根永远是高（或低），译码结果被限制在很小的范围里。
3. "全亮不灭"那次是另一回事：量段选端口发现**段选限流电阻的一排排阻没插实**，P0 上的段码时有时无，表现为乱亮；另外确认位选其实一直在快速切换，只是段选常亮导致视觉上"全亮"。

**根本原因**
两个不同层次的原因：
1. **译码器输入缺一路**：3-8 译码需要 `A/B/C` 三路全对，缺一路就会把 8 个位号映射到一个错误的子集上，表现为"只亮几位"。
2. **段选驱动不可靠**：P0 是开漏口，必须经缓冲（板上是 74HC245）并串限流电阻。排阻接触不良或阻值不对，段码就会"忽明忽暗/全亮/常亮"。

**解决办法**
1. **接线逐脚核对**：把 `A→P2.2`、`B→P2.3`、`C→P2.4` 三根线单独插拔一次确认到底，并写了一个**自检模式**（`config.h` 里的 `SELFTEST_MODE`，置 1 重新烧录）——程序按固定节奏依次点亮每一位、每个段，接线错一眼就能看出来。
2. **按压排阻与排线**：段选排阻重插，P0 排线重压，确认 74HC245 的使能脚接对。
3. 把"数码管自检"列为**演示前必检项**（见文档 08 的检查清单）。

**经验总结**
数码管不亮或者乱亮，**先分清是"位选问题"还是"段选问题"**：只亮固定几位 → 位选（74HC138 输入）；亮度散乱、笔画乱 → 段选（P0 缓冲与限流）。分清了再去查线，比盲目拔插快得多。另外**自检模式救了我很多时间**——这类问题靠看代码看不出来，必须有一个"让硬件自己说话"的模式。

## 问题 9：按键要按住很久才有反应

**现象**
功能都对了，但按键**迟钝得离谱**：按一下 K3 没反应，要按住大概一秒钟才切换模式；按 K4 调温度，我只能一秒一下地按，快了就丢；有时候明明按了却没反应。

**排查过程**
1. 先查消抖：我的消抖是 40ms（`KEY_DEBOUNCE_MS`），不该这么迟。
2. 在按键扫描函数里翻转一个 LED 打时间戳，发现**按键扫描函数大约 1 秒才被调用一次**——扫描本身没问题，是**它根本没被及时调用**。
3. 往上追主循环：

```c
/* 阻塞式主循环 —— 按键被饿死 */
while (1) {
    ds_start_convert();
    delay_ms(800);          /* ★ 这里死等 800ms，什么都没干 */
    ds_read_scratchpad(&raw);
    key_scan();             /* 800ms 才轮到一次 */
    display_refresh();      /* 又是几百微秒 */
}
```

**根本原因**
**主循环被 DS18B20 的转换等待阻塞了。** 我为了等 750ms 转换（问题 1 的解决办法），直接写了 `delay_ms(800)` 死等。这 800ms 里 CPU 什么都不能做，按键扫描 800ms 才轮到一次，所以按键必然迟钝。

**解决办法**
彻底改成**非阻塞时间片调度**：
1. **主循环里不再有任何 `delay`**，所有周期性任务用"时间戳 + 到点执行"的方式轮询（温度采样 1000ms、状态机判定 100ms、显示数据刷新 200ms、串口上报 1000ms）。
2. **按键扫描搬进定时器中断**，每 **20ms**（`KEY_SCAN_MS`）执行一次，连续 2 次（40ms，`KEY_DEBOUNCE_MS`）同电平才确认按下，按住超过 **1500ms**（`KEY_LONG_MS`）判长按。
3. DS18B20 的转换等待改成"发起转换 → 记时间戳 → 到点回来读"，等待期间主循环正常跑。
4. **PWM（200µs）和数码管扫描本来就在定时器中断里**，完全不受影响。

改完后：按键响应主观感受是"立刻"，长按判定也稳定。

**经验总结**
**在嵌入式主循环里写 `delay()` 就是在偷处理时间。** 一个长 delay 会同时破坏按键响应、显示刷新、通信响应——所有靠轮询的东西。正确的模型是**"状态机 + 时间戳"**：每个任务记住"我上次什么时候执行的"，主循环只问"现在到点了吗"。中断处理硬实时的（PWM、扫描、按键），主循环处理软实时的（状态机、上报）。

## 问题 10：串口收发乱码

**现象**
串口助手接收区全是乱码（`烫烫烫`、奇怪的符号），或者偶尔有一两个正常字符夹在乱码里。用 `STATUS` 命令测试，板子有时候回、有时候不回，回的也是乱码。

**排查过程**
1. 先确认串口助手参数：重新设置成 **9600 / 8 位数据 / 无校验 / 1 位停止位**，取消"16 进制显示" → **还是乱码**，说明不是助手设置的问题（但这一步必须先做，否则会浪费很多时间）。
2. 检查定时器 1 的波特率重装值和 SMOD 位：核对计算没错。
3. **量晶振**：用频率计/示波器量单片机的 XTAL 脚，实测 **12.000MHz**，不是 11.0592MHz！问题找到了。
4. 算一下误差。11.0592MHz 下**一个机器周期 = 12 / 11.0592MHz ≈ 1.085µs**。定时器 1 方式 2（8 位自动重装，SMOD=0）算 9600bps 需要每次溢出 **3 个机器周期**，重装值是 `256 − 3 = 253 = 0xFD`，得到 `1 / (3 × 1.085µs × 32) = 9600.0bps，误差 0%`。
   可如果晶振实际是 12MHz、代码却按 11.0592MHz 写 0xFD：机器周期变成 1.0µs，实际波特率 ≈ 10434.8bps，**比 9600 高约 8.7%**，必然乱码。
   更根本的是 **12MHz 晶振本身凑不出干净的 9600**：能取到的重装值只有 252 或 253，对应 **8928.6bps（−7.0%）** 或 **10416.7bps（+8.5%）**，**两个方向都远超 UART 能容忍的 2%~3%**。这就是 51 串口必须用 11.0592MHz 的原因。

**根本原因**
**晶振频率与波特率计算不匹配。** 11.0592MHz 之所以被选为 51 的标准晶振，就是因为用它算 9600bps 时**重装值正好是整数 `0xFD`（253），误差 0%**；而 12MHz 无论怎么取重装值都凑不出 9600，只能取到 8928.6bps 或 10416.7bps，**误差分别为 −7.0% 和 +8.5%，都远超 UART 可接受的 2%~3%**。我买/用的是 12MHz 的板子，但代码按 11.0592MHz 算重装值，于是波特率整体偏了——**这个误差会表现为"偶尔错一两个字节"到"完全乱码"之间的各种程度，很容易被误判成干扰或线材问题**。

**解决办法**
1. 最正确的做法：**换成 11.0592MHz 晶振**（这是 51 串口通信的标准配置，误差 0）。
2. 工程上更省事的做法：既然我把晶振频率做成了配置项，**只改 `config.h` 一行**，重装值自动跟着重算：

```c
#define FOSC_HZ  11059200UL   /* 如果你的板子是 12MHz，只改这一行 */
```

定时器重装值、PWM 定时参数都由这个宏推导，改完重新编译即可。
3. 另外检查了两个容易一起犯的错：**波特率与校验位/停止位设置**（确认 8N1）、**发送时是否带换行**（协议要求每条命令以换行结尾，不带换行命令不会被解析，看起来像"板子不理我"）。

**经验总结**
**串口乱码的顺序是固定的**：先查上位机参数（9600 8N1）→ 再查晶振频率是否与重装值匹配 → 最后才怀疑线材和干扰。这次让我印象最深的是**"误差只有几个百分点"的故障**：8.7% 的偏差不会让你完全不通，而是时好时坏，比彻底不通难查得多，也最能说明"11.0592MHz 不是随便选的数字"。

## 问题 11：Keil 编译报 L250 / L104，"code size limit exceeded"

**现象**
代码写到一半（加了串口命令解析、状态机、显示之后），Keil 编译突然报错，最典型的是这一条：

```
*** FATAL ERROR L250: CODE SIZE LIMIT IN RESTRICTED VERSION EXCEEDED
```

同时链接阶段还会连带报出 `L104` 一类的链接错误，`.hex` 根本生不出来。我一开始按"链接错误"去查（怀疑符号重定义、库冲突），翻了半天毫无进展——因为代码本身没有错，是**Keil C51 未注册（Evaluation）版本的 2KB 代码体积上限**被顶破了。

**排查过程**
1. 先排除真错误：把最近加的代码一段段注释掉，发现**每一段单独看都能编译过，只要整体代码量降到 2KB 以下就过**——说明不是语法/符号问题，是容量限制。
2. 看 Keil 的 Build Output，确认 `Program Size: code=...` 已经超过 **2048 字节**。
3. 确认是未注册版：Help → About 里显示 Evaluation Version。
4. 顺便学到一个判据：**`L250` 这类"RESTRICTED VERSION"字样才是体积限制**，而普通的符号重定义/未定义符号是另一类错误——两条不要混在一起查，否则会浪费时间。

**根本原因**
**Keil C51 的评估版对生成的代码体积有 2KB 硬上限**，超了就报 L250。这是授权限制，不是代码质量问题。而我的工程即使精简，加上 1-Wire 时序、状态机、串口解析、数码管扫描这些"必需代码"，本来也会逼近这个量级——所以必须主动减体积。

**解决办法**
三条路，我都了解并采用了以第三条为主的组合方案：

**（1）注册/使用正版授权**
最直接。有授权就直接解决，工程不用改一行。课程环境不一定有，但值得先问实验室。

**（2）改用 SDCC（开源免费、无体积限制）**
SDCC 是免费开源的 8051 编译器，没有 2KB 限制。代价：语法扩展和 Keil 有差异（比如 `sbit`/`srf` 的关键字写法、中断函数声明方式、存储类型关键字），需要单独维护一份移植层。适合长期项目。

**（3）裁剪代码（我在做的）**
- **关掉 `printf`**：Keil 的 printf 会拖进格式化和浮点支持，体积巨大。我改成手写串口发送函数 + 定点拆位，只输出我需要的 10 个字段；
- **用 `code` 关键字把常量表放进 ROM**：数码管段码表、状态名字符串表全部声明为 `code`，只占 Flash 不占 RAM；
- **彻底不用浮点**（对应问题 3 的定点方案），省下整个浮点库；
- **中断服务程序尽量短**，重复逻辑合并成函数；
- **编译时开优化**（Keil 的 Level 8 优化）。

最后代码体积压到 2KB 以内，`.hex` 正常生成。

**经验总结**
2KB 限制一开始让我很烦躁，但事后看，**它逼我建立了 8 位机的编码习惯**：定点数代替浮点、查表代替计算、`code` 关键字、位操作、状态机代替长函数。这些习惯在任何资源受限的 MCU 上都是对的。**限制不是障碍，是老师。**

## 问题 12：Keil 报 "declaration may not appear after executable statement"

**现象**
我在一个函数里这样写（写惯了现代 C）：

```c
void state_machine(void)
{
    u8 st = get_state();
    handle(st);

    u8 next = calc_next();     /* ★ 在语句之后声明变量 */
    ...
}
```

Keil 直接报错：
```
error C100: unprintable character ...
error C231: 'next': redefinition
```
最典型的是这一条：
```
error C100: ... declaration may not appear after executable statement in block
```
编译不通过，而且报错位置常常在我觉得"完全正确"的那一行。

**排查过程**
1. 把报错行上下看一遍：语法在我认知里是对的 → 说明是**语言标准版本**问题。
2. 查 Keil C51 文档：**Keil C51 默认按 C89（ANSI C）编译，C89 要求一个块里所有变量声明必须出现在任何可执行语句之前。**
3. 排查整个工程，发现这种"中途声明"我写了好几处（因为平时写 C99/C++ 习惯了）。

**根本原因**
**C89 与 C99 的语法差异。** C99 允许"声明与语句混排"，C89 不允许。Keil C51 是 1980 年代末的产品，默认遵循 C89。我下意识地按 C99 写，编译器不认。这类问题烦人的地方在于：**代码在现代编译器下完全正确，只在 Keil 下报错**，容易误以为是自己逻辑写错。

**解决办法**
1. **全工程统一写成 C89**：所有局部变量声明放在函数/块的最前面，声明区之后才写执行语句。
2. 这成为本工程的**编码规范**，并写在 `config.h` 的文件头注释里：

```c
 *          编译器：Keil C51（uVision5）  ★ 本工程全部使用 C89 语法
```

3. 顺手统一的还有几条 C89 约束：不用 `//` 单行注释改用 `/* */`（部分老编译器对 `//` 支持不好）、不用变长数组、不用 `inline`。另外发现过一次真正的乱码报错（`unprintable character`），根源是**中文全角标点混进了代码**（比如全角分号 `；`），这个要单独查。
4. **把编译报错当成规范检查**：Keil 报错指向哪一行，先看"声明位置"和"标点是不是英文"，这两条命中率极高。

**经验总结**
**写嵌入式 C 一定要知道自己在哪一套标准下。** 不要用桌面编译器的习惯直接套上 MCU。而且这类"语法正确却编译不过"的问题，最快的解法不是改逻辑，而是**回到标准去读一眼**——我为了这个问题第一次认真读了 C89 和 C99 的差异，之后整个工程再没犯过。

## 问题 13：下载后程序不运行 / STC-ISP 握手失败

**现象**
三种表现都遇到过：
1. 点"下载"，STC-ISP 卡在"正在检测单片机..."，最后报**握手失败**；
2. 提示下载成功，但**板子上一点反应都没有**（数码管不亮）；
3. 下载成功、刚才还能跑，改了一行重新下载就再也下不进去了。

**排查过程**
1. 先排查"串口被占用"：发现**串口助手还开着**，它和 STC-ISP 抢同一个 COM 口。关掉串口助手后，握手成功率明显提升。
2. 还失败的时候，查"冷启动"：STC 系列单片机**必须冷启动进 ISP**——也就是**先点下载按钮，再给板子上电**，单片机在复位后的极短时间里检测下载流。我一直是"上电 → 点下载"，顺序反了，所以单片机早就跑进用户程序了，检测不到下载流。
3. 还有一次是 **COM 口选错**：电脑上插了 USB 转串口，助手和 ISP 里选的不是同一个口。
4. "下载成功但不运行"那次：查出来是**烧的 hex 是旧路径的**（Keil 输出目录有两个同名 hex），另外一次是**上电后没复位**，手动按一下复位键就跑了。

**根本原因**
四个独立原因，且都有"看起来一样"的错误提示，必须按顺序排除：
1. **串口被占用**：STC-ISP 和串口助手不能同时打开同一个 COM 口；
2. **没有冷启动**：STC89C52RC 靠"上电瞬间"进入 ISP 下载模式，不冷启动就永远握手失败；
3. **COM 口错误**：多串口环境下选错；
4. **烧错文件 / 未复位**：路径里存在旧 hex；或下载后需要复位才启动。

**解决办法**
形成固定的下载流程（也写进了演示检查清单）：

- [ ] 关闭串口助手（以及任何占用串口的软件）
- [ ] 设备管理器确认 COM 号（拔插一次，看哪个 COM 消失/出现）
- [ ] STC-ISP 选对 COM 口、型号选 **STC89C52RC**、晶振填 **11.0592**
- [ ] 选对 `.hex` 路径（和 Keil 输出目录一致）
- [ ] **先点"下载/编程"，再给板子冷启动**（关电源开关再开，或拔插 USB）
- [ ] 看到"操作成功"提示
- [ ] 若程序不动，按一次复位键；仍不动则拔掉电机再上电（排除电源跌落，见问题 4）
- [ ] 需要看串口输出时，**下载完再打开串口助手**

**经验总结**
**下载失败的第一反应应该是"顺序对不对"和"口有没有被占"，而不是"程序写错了"。** 因为"握手失败"根本还没到运行程序的阶段，跟代码无关。另外**"下载成功但不运行"要优先怀疑烧错文件**——这个问题我犯过一次，浪费了半小时在那个"明明编译成功了"的 hex 上。

## 问题 14：电机低速档（34%）时几乎不转，只有嗡嗡声

**现象**
四档都通了之后发现：**全速（100%）和中速（66%）转得很好**，但**低速档（34%）几乎不转**——电机只有轻微的嗡嗡声和抖动，转子不连续旋转，用手一碰就停。用串口发 `LEVEL 1` 复现，同样现象。

**排查过程**
1. 先确认软件：串口帧 `DUTY=34`、`LEVEL=1`，P1.0 用示波器量是干净的 100Hz、34% 占空比方波 → **PWM 波形是对的**。
2. 量电机两端电压：34% 占空比下有约 1.7V 平均电压，但示波器上看电流波形——**电流几乎断续**。
3. 分析转矩：直流电机的转矩与平均电流成正比，而**启动/低速时反电动势（反电压）很小，需要更大的电流才能建立转矩**。34% 占空比虽然电压平均值有 1.7V，但 100Hz 的斩波下，**每个周期通电只有 3.4ms，而电机绕组的电感常数不允许电流在这段时间里建立到足够值**，于是电流断续、转矩不足。
4. 又想到问题 4 里的经验：**当时还没加续流二极管**，PWM 关断期间电机绕组的电流没有泄放回路，被强行切断，本来就削弱了转矩。

**根本原因**
**低占空比下电机转矩不足**，是三个因素叠加：
1. **占空比太低**：34%（17/50 级）在 100Hz 下通电窗口只有 3.4ms，对这个小电机的绕组时间常数来说偏短；
2. **PWM 频率偏低**：100Hz 意味着每个周期 10ms，电流脉动大，低速时更容易断续。频率提高（比如 1kHz）可以让电流更连续，但要在软件开销和电机特性之间权衡；
3. **缺少续流回路**：关断瞬间绕组电流被切断，能量无处泄放，进一步削弱平均转矩。

**解决办法**
几个方案按代价从低到高：
1. **把最低档占空比提高**：`DUTY_LOW` 从 17（34%）提到 **20（40%）**。这是最省事的做法——低速档本来就是"轻微散热"，不需要极低转速，40% 起转更可靠。**注意：这是参数改动，只需改 `config.h` 一行，重新编译。**
2. **加续流二极管**（和问题 4 同一个措施）：**电机两端反并联 1N4007**（阴极接 +5V、阳极接 OUT），给关断电流一条泄放回路，能明显改善低速启动力矩。
3. **提高 PWM 频率**：减小 `PWM_ISR_US`（比如 200µs → 100µs）或增大 `PWM_LEVELS`，让电流脉动更小、更连续。代价是中断更频繁、CPU 开销上升，需要重新验证 2KB 代码和实时余量。
4. **兜底做法**：接受 34% 是有条件的低速档——只要保证它"能转起来"而不是"嗡嗡不动"即可；如果换了电机型号，重新测一次最低可起转占空比。

最终我选了 **1 + 2 组合**（40% + 续流二极管），实测在最低档能稳定起转，用手轻捏能感觉到明显但可停住的转矩。

**经验总结**
**PWM 调速不是"占空比线性对应转速"的。** 在小电机上存在一个**最低起转占空比**，低于它电机只会嗡嗡响、发热、不转——既不散热又白耗电。这个下限由电机参数、PWM 频率、续流回路共同决定，**必须实测，不能拍脑袋写 30%**。

## 问题 15：温度读数偶尔跳变、CRC 校验错

**现象**
大部分时候读数正常，但**偶发**：串口帧里 `T` 突然跳一个很离谱的值（比如从 `35.0` 跳到 `67.0`），或者 `SENSOR` 字段偶尔出现 `BADCRC`。不是每次都有，大概几十秒一次；电机转起来之后概率变高。

**排查过程**
1. 先确认不是软件换算错：跳变的那一帧第二天再复现，同样的值不可能靠逻辑产生，说明是读到的原始数据被扰动。
2. 复现规律：**电机开启时更容易出现** → 干扰源找到了，是电机换向产生的电噪声耦合到 1-Wire 总线上。
3. 再看得更细：算了一下我的读时隙采样点位置，发现我当初把采样点写得**比较靠近拉低沿**（约 8~9µs），边沿还没完全建立就开始采样，任何一点额外干扰就采错。
4. 还有一个隐蔽原因：**1-Wire 的位操作在读时隙中间被中断打断**。我的定时器中断每 200µs 一次，如果某次中断恰好落在读时隙的关键窗口里，读操作被推迟，采样点漂移 → 读错。

**根本原因**
三个因素合在一起：
1. **采样点太靠边**：DS18B20 规定主机应在拉低后 **15µs 内**采样，但"在 15µs 内"不等于"越早越好"。贴近拉低沿采样，边沿建立不完整，抗干扰余量最小。
2. **中断干扰时序**：1-Wire 的短时隙（µs 级）与定时器中断（200µs 级）不在一个时间尺度上，一次中断就可以让采样点偏移几µs，足以采错。
3. **CRC 没被用作判据**：早期版本我只读了原始字节，没有严格校验 CRC，读错了也不知道。

**解决办法**
1. **采样点固定在拉低后约 11µs**——放在 15µs 窗口的**中段**，左右都留余量。这是"宁可在窗口中间，不在窗口边缘"的原则。
2. **位操作期间关闭中断**：对 1-Wire 的读/写单个时隙这段很短的临界区**临时关闭定时器中断**，做完立刻开回来（临界区只有十几µs，对 PWM 的 200µs 周期影响可以忽略）。
3. **严格校验 CRC**：每读一次暂存器都算 CRC，失败就报 `BADCRC`，并**计入连续失败计数**（`DS_FAIL_LIMIT = 3`，连续 3 次失败进 FAULT）。这样偶发错误不会污染数据，连续错误会被识别为故障。
4. **电机侧加续流与滤波**（对应问题 4），从源头减少干扰。

**经验总结**
**µs 级的时序协议在面对 ms 级的中断时必须显式保护。** 这是我第一次真正理解"临界区"为什么存在——不是理论概念，是因为一个 200µs 的中断真的会把一个 11µs 的采样窗口打歪。另一条经验：**能校验的数据一定要校验**，CRC 不是可选的装饰，它把"偶发错误"和"传感器故障"区分开了。

## 问题 16：串口收命令丢字符、粘包

**现象**
用串口助手连续快发命令时，板子会**丢字符**（`MODE MANUAL` 变成 `MODE MANU`，解析失败）或者**粘包**（`SIM T=45.0SIM T=25.0` 连在一起，两个命令只生效一个）。慢一点发就正常。

**排查过程**
1. 先确认硬件：9600 波特率下每字节约 1.04ms，慢发没问题 → 不是电气问题。
2. 看接收代码：

```c
/* 早期版本 —— 主循环里轮询一个字节 */
while (RI == 0) { }      /* 死等一个字节 */
c = SBUF; RI = 0;
```

分析：这样"收一字节 → 处理一字节"的写法，**主循环在处理上一个字节时，下一个字节已经到了**（1.04ms 一个字节，而我的处理可能更慢），`SBUF` 被覆盖，字符就丢了。
3. 粘包则是另一个问题：我按"固定长度"或"读到换行前的所有字节"来处理，但如果两条命令的换行间隔太短，我一次读到的缓冲里就装了两条命令，而解析函数只解析第一条。

**根本原因**
1. **没有接收缓冲**：一个字节的 `SBUF` 寄存器无法承受连续字节到达，必须用**环形缓冲（FIFO）**在中断里把字节存起来，主循环再从缓冲里取。
2. **没有按行组帧**：串口是字节流，命令之间必须有明确的分帧符。我的协议规定**每条命令以换行结尾**，所以接收端应该"**收到换行才算一帧**"，而不是"读一次就当一帧"。

**解决办法**
1. **接收中断 + 环形缓冲**：串口接收中断里只做一件事——把 `SBUF` 存进环形缓冲并移动写指针。缓冲区大小取 `UART_RX_SIZE 32`（`config.h` 里定义），够放最长的命令。
2. **按换行组帧**：主循环从环形缓冲里逐字节取，**遇到换行（或缓冲满 `LINE_MAX 40`）才把一整行交给解析函数**。这样无论是丢字符还是粘包都解决了。
3. **命令解析做成"前缀 + 参数"的表驱动**：`SIM` / `MODE` / `SET` / `LEVEL` / `STATUS` / `RESET` 六条命令各自匹配前缀，参数用定点解析（`T=45.0` → `450`，支持小数和负数）。
4. **发送侧也做缓冲**：一帧最长约 60 字节，取 `UART_TX_SIZE 96` 足够，发送用中断或短等待，避免和接收抢时间。

**经验总结**
**串口编程的正确姿势是"中断收、缓冲存、按帧解析"**，绝不能在主循环里"轮询一个收一个"。同时，**任何字节流协议都必须定义清楚分帧规则**（我这里是换行结尾），否则接收端永远无法知道一帧到哪里结束。

## 问题 17：状态在临界点反复跳、蜂鸣器乱叫

**现象**
改了回差之后（问题 5），大部分时候好了，但有个新毛病：**报警会自己反复触发又解除**，蜂鸣器"嘀——嘀——嘀"断断续续响个不停，声音比连续报警还刺耳；串口日志里 `ST` 在 `ALARM` 和 `MID` 之间来回跳。

**排查过程**
1. 看日志，发现跳变发生在 `T` 恰好在解除阈值附近时。我当时实现的解除逻辑是：

```c
/* 早期版本 —— 瞬时判定 */
if (T <= TSET + ALARM_EXIT) {
    alarm = 0;            /* 只要一低于阈值立刻解除 */
}
```

温度一低于 `Tset+4.0℃` 立刻解除，一高于 `Tset+8.0℃` 立刻触发——但温度在这之间来回晃，于是反复跳。
2. 又发现一个更根本的错误：我的档位判定里，**升档和降档的阈值方向用反了**——本来应该"温度上升才升档、下降到更低的阈值才降档"，我写成了"只要 T 高于某个值就升档"，等于**两套阈值变成了同一套**，死区没起作用。
3. 用日志验证：一个 20 秒的窗口内，`ST` 状态变化了 30 多次。

**根本原因**
两个错误，一个是逻辑错误，一个是设计缺失：
1. **回差方向写反**（逻辑错误）：回差的意义是"**升档用一个阈值、降档用另一个更宽松的阈值**"。如果两个方向判断时用了同一组比较，死区就不存在，等于没做回差。
2. **报警解除没有"保持时间"**（设计缺失）：即使有 4.0℃ 的死区，如果温度恰好在死区里来回晃（比如风吹），仍然可能反复触发。**报警这种"打扰用户"的输出，解除条件里必须加时间维度。**

**解决办法**
1. **把状态机改成显式的"当前档位 + 目标档位"比较**，升档和降档走不同的阈值分支，代码结构上就保证不会用错：

```c
/* 升档看 ENTER 阈值，降档看 EXIT 阈值 —— 分支必须分开写 */
switch (level) {
case LV_STOP:
    if (T >= TSET + LV_ENTER_LOW)  next = LV_LOW;      /* 升档 */
    break;
case LV_LOW:
    if (T <= TSET + LV_EXIT_LOW)   next = LV_STOP;     /* 降档 */
    else if (T >= TSET + LV_ENTER_MID) next = LV_MID;  /* 升档 */
    break;
case LV_MID:
    if (T <= TSET + LV_EXIT_MID)   next = LV_LOW;
    else if (T >= TSET + LV_ENTER_HIGH) next = LV_HIGH;
    break;
case LV_HIGH:
    if (T <= TSET + LV_EXIT_HIGH)  next = LV_MID;
    break;
}
```

2. **报警加最短保持时间**：`ALARM_HOLD_MS 5000`——一旦进入报警，**至少保持 5 秒**；5 秒后如果 `T ≤ Tset+4.0℃` 才允许解除。这样温度在窗口里乱晃也不会造成蜂鸣器断续。
3. **状态判定周期固定为 100ms**（`TICK_MS`），不在中断里立刻改状态，天然有一点平滑效果。
4. 用串口日志做**回归验证**：连续观察 60 秒，统计状态切换次数，确认从 30 多次降到个位数。

**经验总结**
**回差必须"两套阈值、两个分支"，写成一套就退化成了单阈值。** 另外，**面向人的输出（蜂鸣器、报警灯）一定要有最短保持时间**——因为人的感知需要时间，闪一下就过去的报警等于没报，而频繁开关的报警比持续报警更烦人。这两个教训合起来就是一句话：**控制逻辑要考虑"时间维度"，不只是"数值维度"。**

## 问题 18：仿真模式（SIM）只是"假数据"，会不会掩盖真实问题？

**现象与困惑**
为了保证被问到时能稳定演示 8 个状态，我做了 `SIM T=xx.x` 串口注入命令（注入模拟温度、进入仿真模式）。但有同学/老师质疑：**"你这是假数据，是不是绕过了真实传感器？那你的控制逻辑还算数吗？"** 我自己一开始也答不上来，心里不确定这个功能算不算"作弊"。

**排查与思考过程**
1. 先明确目的：我为什么要做 `SIM`？因为**真实加热/降温慢且不稳定**——用吹风机把温度吹到 43.0℃ 以上可能要好几十秒，而且一松手就掉；用按键改目标温度能做出 STOP→HIGH 的跳变，但**做不到精确的中间档位和报警阈值的稳定复现**。
2. 再看实现方式：注入的值**替换的只是"温度读数"这一个变量**，它进入的仍然是**同一个状态机、同一套回差阈值、同一个 PWM 输出、同一个报警判定、同一份串口协议**。
3. 关键验证：**在仿真模式下拔掉 DS18B20，程序是否还会进 FAULT？** 答案是**会**——因为 1-Wire 的读取探针**在后台照常运行**，仿真只替换温度数值，不屏蔽传感器健康检测。串口帧里 `SIM=1`、`SENSOR=NOPRESENT` 会同时出现。
4. 于是定位清楚了：**`SIM` 是"传感器数据源"这一层的替换，不是"控制逻辑"的旁路。**

**根本原因**
这不是一个技术问题，而是一个**设计边界的表述问题**。`SIM` 如果实现成"直接把状态写成 STOP / ALARM"，那就是作弊（跳过了控制逻辑）；实现成"只替换温度输入值"，那就是**标准的注入测试**（控制逻辑完整走一遍）。我的实现属于后者，但我一开始没有把这个边界讲清楚，所以看起来可疑。

**解决办法**
1. **明确实现边界**：`SIM T=xx.x` 只覆盖温度输入变量，并置 `SIM=1` 标志；`SIM OFF` 恢复真实传感器。状态机、回差、PWM、报警、上报**一行都不绕过**。
2. **保持传感器健康检测独立运行**：仿真模式下仍执行 1-Wire 读取探针，故障判定照常生效（连续 3 次失败进 FAULT）。这样 `SIM` 不会掩盖真实硬件问题。
3. **在协议里显式暴露**：串口帧第 10 个字段 `SIM` 明确标出当前是否处于仿真，第 11 个字段 `SENSOR` 用 `OK / NOPRESENT / BADCRC / NOINIT` 报告真实传感器状态。**两个字段一起看，就知道"温度值是不是注入的、真传感器有没有坏"**。
4. **讲解表述固定下来**："`SIM` 是给自动化测试和现场演示用的**数据注入接口**，它替换的是传感器读数，不是控制逻辑。所以我能用它把 8 个状态全部稳定复现，而且**注入模式下拔掉传感器照样进 FAULT**。"

**经验总结**
**调试/测试功能必须有清晰的"作用边界"，并且在对外接口上可见。** 一个"能造数据"的功能如果没有边界说明，就容易被当成掩盖问题的手段；而如果把边界写清楚（只注入输入、不跳过逻辑、健康检测独立、状态字段公开），它就变成了一个正当的**注入测试接口**——工业控制器上对应的就是"仿真/调试模式"。

## 如果重做一次，我会怎么改

如果给我更多时间重做这个项目，我会按下面 5 条来改。每条都对应上面复盘中暴露出来的真实短板。

### 1. 换成带硬件 PWM 的 MCU（STC15 / N76E003 的 PCA/PWM 模块）

**为什么**：现在 PWM 是**定时器 0 每 200µs 中断一次、软件计数 0~49 比较翻转 IO**（`PWM_LEVELS 50` / `PWM_ISR_US 200` → 100Hz）。这占用了 CPU 每 200µs 一次的中断——虽然目前跑得动，但这是我的实时余量里最大的一块开销，也是问题 15（中断干扰 1-Wire 时序）的根源之一。

**怎么改**：用 STC15 或 N76E003 的 **PCA / 硬件 PWM 模块**，把波形生成完全交给硬件。好处：① CPU 从 200µs 中断里解放，主循环余量大增；② PWM 频率和占空比精度都能提高（解决低速档转矩不足，问题 14 可选的"提高频率"方案）；③ 1-Wire 的 µs 级时序不再被中断打断。

**代价**：换芯片意味着重新画板/改接线，`config.h` 的引脚定义要改——但我的工程本来就是"换板子只改 config.h"，这正是当初做参数分离的价值。

### 2. 加 NTC 冗余测温，做传感器交叉校验

**为什么**：现在**只有一路 DS18B20**，所以对它的信任是"全信"或"全不信"（`DS_FAIL_LIMIT = 3` 连续失败就进 FAULT）。问题是有些故障不是"读不到"，而是"读到错的"——比如传感器漂移、被遮挡、贴在发热元件旁边。单传感器系统没法识别这类故障。

**怎么改**：加一路 **NTC 热敏电阻 + 分压 + ADC**（或者第二路 DS18B20）作为冗余，**两路温度交叉校验**：
- 两路温差 < 3℃：取平均或取更保守的值（用于控制）；
- 两路温差 > 5℃ 且持续 10s：判"温度测量不可信"，进降级/保护状态；
- 一路失效：**自动切到另一路继续工作**（这叫降级运行，比直接停机体验好），并在串口帧里报出哪一路故障。

这一条直接对应问题 1、2、15 的教训——**"读不到"能检测，"读错了"检测不了，冗余是唯一解**。

### 3. 用旋转编码器代替两个按键

**为什么**：现在 K4 每次只加 **1.0℃**（`TSET_STEP 10`），要从 35.0℃ 调到 20.0℃ 要**按 15 次**（文档 08 里的"一键演示"其实是在掩盖这个交互缺陷）；两个按键靠"短按/长按 + 模式"硬凑出 6 种操作（问题见文档 08 Q11），逻辑复杂且容易误操作。

**怎么改**：换**带按键的旋转编码器（EC11）**：
- 旋转 = 连续调温度，快转快调、慢转微调，**不用按 15 次**；
- 按下 = 确认 / 切换模式；
- 长按 = 恢复默认。

交互从"离散按键组合"变成"连续输入 + 一个确认键"，代码上只需要一个正交解码状态机 + 一个按键，比现在的"短按/长按判定"更简单也更不容易误触。

### 4. 加 I2C OLED 显示温度曲线

**为什么**：现在显示只有**8 位共阳数码管**（段选 P0 经 74HC245、位选 P2.2/P2.3/P2.4 经 74HC138），能显示当前温度和设定值，但**看不到趋势**——温控系统的核心信息恰恰是"温度在往上走还是往下走、离报警还有多远"。而且数码管还有问题 6（重影）、问题 7（位序反）、问题 8（接线）这一堆坑。

**怎么改**：加一块 **0.96 寸 I2C OLED（SSD1306）**，只用 2 根线（SDA/SCL）：
- 显示最近 60 秒的温度曲线（滑动窗口，用定点数组存历史值）；
- 画出 Tset 和报警阈值的参考线，**一眼看出"离报警还差多少"**；
- 保留数码管显示当前温度做主显示。

好处：功能上信息量大增；技术上正好补上 **I2C 总线**这一课（我现在只有 1-Wire 和 UART 的经验）。

### 5. 把参数存到 EEPROM，掉电不丢

**为什么**：现在 Tset 默认 `350`（35.0℃），**一掉电就回到默认值**。演示中我用"K3 长按 1.5s 恢复默认（Tset=35.0℃、退出仿真、清报警）"和串口 `RESET` 来复位，说明参数是易失的——用户每次上电都要重新调，这是明显的产品化短板。

**怎么改**：用 **STC89C52RC 的片内 EEPROM**（或外挂 24C02）保存参数：
- 保存内容：`Tset`、四档回差阈值（`LV_ENTER/EXIT_*`）、报警阈值（`ALARM_OFFSET` / `ALARM_EXIT` / `ALARM_HOLD_MS`）、手动模式档位；
- **写入策略**：不能每次按键都写（EEPROM 有擦写寿命，10 万次量级），用"**参数改变后延时 5 秒写入 + 掉电前写入**"的合并策略；
- **加校验**：存一个 CRC 或版本号，读出来校验失败就用 `TSET_DEF` 等默认值并报错——**EEPROM 数据也不敢无条件相信**（和问题 15 的 CRC 校验是同一个原则）。

这一条和问题 17 的经验连起来：**参数是要跨掉电存活的"状态"，而状态要有校验和默认值兜底。**

### 一句话总结这 5 条

| # | 改动 | 解决的问题 |
|---|---|---|
| 1 | 换带硬件 PWM 的 MCU（STC15 / N76E003） | CPU 开销、中断干扰 1-Wire、PWM 精度 |
| 2 | NTC 冗余测温 + 交叉校验 | 单传感器无法识别"读到错的" |
| 3 | 旋转编码器代替按键 | 调温度要按 15 次、按键组合复杂 |
| 4 | I2C OLED 显示温度曲线 | 看不到趋势、数码管一堆显示坑 |
| 5 | 参数存 EEPROM + 校验 | 掉电丢参数、上电要重设 |

**共同思路**：从"能跑通"走向"**可信、好用、可维护**"——**传感器要冗余、人机交互要连续、状态要持久、参数要可解释。**

## 补充：装上 Keil 之后，真编译器又揪出 4 个问题

> 上面 18 个问题是**照着代码和硬件推理**写出来的 —— 写那份内容的时候，这台机器上还没有任何 C 编译器，只能用 Python 做静态检查。
> 后来装好 **Keil C51 V9.60.7**，用真编译器把工程完整跑了一遍，又发现了 4 个**只有编译器能发现**的问题。
> 这 4 个恰好说明了为什么"静态检查替代不了编译"。

### 问题 19：`data` 空间溢出 37 字节，链接直接失败

**现象**
11 个文件全部 `0 WARNING(S), 0 ERROR(S)` 一路顺畅，结果链接这一步直接躺下：

```
*** ERROR L107: ADDRESS SPACE OVERFLOW
    SPACE:   DATA
    SEGMENT: ?DT?KEY
    LENGTH:  0014H
（同样的报错还出现在 ?DT?SMG / ?DT?UART / ?DT?MOTOR 上）
Program Size: data=165.0 xdata=96 code=5254
LINK/LOCATE RUN COMPLETE.  7 WARNING(S),  4 ERROR(S)
```

**排查过程**
1. 第一反应是"代码写太大了"，但报错说的是 `DATA` 不是 `CODE`，方向不对。
2. 查 STC89C52RC 的存储结构：标称 512 字节 RAM，但其中**只有 128 字节**（0x00~0x7F）
   是可以直接寻址的 `data`；上面 128 字节（0x80~0xFF）只能间接寻址（`idata`）；
   另外 256 字节是 `xdata`（要 MOVX 指令访问）。
3. Keil 的 Small 内存模型默认把**所有**未经限定的变量都塞进 `data`。
   本工程 `data=165`，**超了 37 字节**。
4. 一算就明白了：`app.c` 一个文件的状态变量就有 80 多字节（其中命令行缓冲
   `s_line[40]` 独占 40 字节），加上 `key.c` 的 20 字节、`smg.c` 的 9 字节……
   128 字节根本装不下。

**根本原因**
**8051 的存储空间是分层的，而"变量"默认都挤在最窄的那一层。**
而且 `data` 还要分一块给栈，实际能留给变量的只有 100 字节出头。
这个问题在任何 C 语言教材里都不会强调，因为 PC 上根本没有这回事。

**解决办法**
给 `app.c` 里的状态变量显式加上 `xdata` 关键字，挪到片内扩展 RAM：

```c
static u16 xdata g_tset;                 /* 目标温度 */
static char xdata s_line[LINE_MAX];      /* 命令行缓冲，40 字节 */
```

结果：

```
Program Size: data=93.0  xdata=175  code=5905      ← 0 错误
```

`data` 从 165 降到 **93**，给栈留出 35 字节。

**为什么不干脆用 `LARGE` 内存模型一键搞定？**
试过了，链接器立刻报 `WARNING L14: INCOMPATIBLE MEMORY MODEL`；
更关键的是，**LARGE 会把中断服务程序里的变量也挪到 xdata** ——
`MOVX` 是 2 个机器周期，而本工程的定时器中断每 **200µs** 就要进一次，
中断里每条变量访问都慢一倍，会把中断周期直接撑爆。
所以最终方案是：**只有 `app.c`（纯主循环、没有实时要求）用 `xdata`，
`timer/smg/key/motor/uart` 这些中断相关的文件全部保持 Small 模型。**

**经验总结**
在 8 位机上，"内存够不够"和"代码大不大"是**两个完全独立**的问题，前者更容易踩。
判断标准就一条：编译后看 `Program Size: data=...`，**必须小于 128**。

### 问题 20：把 `data` 空间的指针传给了要 `code` 指针的函数

**现象**
编译 `app.c` 时报了一条警告：

```
*** WARNING C259 IN LINE 494 OF app.c: 'parameter': pointer: different mspace
```

**排查过程**
第 494 行是 `uart_tx_str(p)`，其中 `p` 是命令行缓冲的指针：

```c
char data *p = s_line;     /* 命令行缓冲在 data 空间 */
...
uart_tx_str(p);            /* 但 uart_tx_str 的形参是 char code * */
```

而 `uart_tx_str` 的定义是：

```c
void uart_tx_str(char code *s);   /* 字符串常量在 code（ROM）空间 */
```

**根本原因**
**Keil C51 的指针是"带内存空间"的。**
`char code *` 是一个 1 字节的 ROM 地址，`char data *` 是一个 1 字节的 RAM 地址。
两者在 C 语法上看着都是"字符指针"，底层却完全不兼容 ——
把 RAM 地址当 ROM 地址用，编译器生成的是 `MOVC A,@A+DPTR`（读 ROM），
**运行时会去读程序存储器里那个位置，串口输出的就是一串毫无意义的字节。**

C51 只在编译期给了一条 `WARNING`（还不是 ERROR）。如果不看警告就烧进去，
串口会打印乱码，而你会以为是波特率问题 —— 能查半天。

**解决办法**
不要跨空间传指针。既然命令行缓冲在 `xdata`（问题 19 之后），
回显时直接按下标遍历：

```c
u8 i;
uart_tx_str("#ERR ");
for (i = 0; i < s_line_len; i++) {
    uart_tx_ch((char)s_line[i]);
}
uart_tx_str("\r\n");
```

（顺带把 `s_line` 的类型也改了：既然它进了 `xdata`，
所有曾经指向它的 `char data *p` 都要改成 `char xdata *p`，否则又是一堆 C259。
改完整个工程才是 0 警告。）

**经验总结**
**在 Keil C51 里，指针的"内存空间"和指针的"类型"同样重要。**
写函数原型时能不省就不省：要 ROM 常量就写 `char code *`，
要 RAM 缓冲就写 `char xdata *`，别图省事写个光秃秃的 `char *`。

### 问题 21：`#if SELFTEST_MODE` 写在 `#include "config.h"` 之前，自检功能静默失效

**现象**
这个最阴。编译 `selftest.c` 时只有一条不起眼的警告：

```
*** WARNING C322 IN LINE 19 OF selftest.c: unknown identifier
C51 COMPILATION COMPLETE.  1 WARNING(S),  0 ERROR(S)
```

编译"通过"、链接也过，**但整个自检程序一行都没被编译进去**。

**排查过程**
`selftest.c` 开头原本是这样：

```c
/* 文件头注释…… */
#if SELFTEST_MODE          ← 第 19 行
#include "selftest.h"
```

而 `SELFTEST_MODE` 是在 `config.h` 里定义的，`config.h` 在 `#if` **后面**才被包含。

**根本原因**
**C 预处理器遇到未定义的标识符，不会报错，而是当成 0。**
所以在 `#if SELFTEST_MODE` 那一刻它还没定义 → 当作 0 →
整个 `#if ... #endif` 块被丢掉 → `selftest.c` 编译成一个空文件。

于是"把 `SELFTEST_MODE` 改成 1 就能进自检模式"这个功能**彻底失效**：
你改了宏、重新编译、烧进去 —— 什么都不会发生，
而编译器只给一条 `unknown identifier` 警告，极容易被忽略。

**解决办法**
把 `#include "config.h"` 提到 `#if` **前面**：

```c
#include "config.h"      /* ★ 必须在 #if 之前 */

#if SELFTEST_MODE
#include "selftest.h"
```

然后在 `config.h` 里把 `SELFTEST_MODE` 改成 1 重新编译，
确认 `code` 从 5905 涨到 7866 —— 说明自检代码这次真的进去了。

**经验总结**
**用宏控制编译时，"宏在哪定义"和"宏在哪儿被判断"的先后顺序是硬性约束。**
一条 C322 警告背后，可能是一个功能完全没生效。

顺便说：这个 bug 靠 Python 静态检查**查不出来** ——
`lint_c51.py` 检查了括号、宏、函数声明、C89 声明位置，全都通过。
**只有真编译器那条 WARNING 暴露了它。**

### 问题 22：自检程序里用了 `delay_ms()` 却没包含 `delay.h`

**现象**
把 `SELFTEST_MODE` 改成 1、按问题 21 修好之后，重新编译：

```
*** WARNING C206 IN LINE 43 OF selftest.c: 'delay_ms': missing function-prototype
*** ERROR   C267 IN LINE 43 OF selftest.c: 'delay_ms': requires ANSI-style prototype
C51 COMPILATION COMPLETE.  1 WARNING(S),  1 ERROR(S)
```

链接跟着崩：

```
*** FATAL ERROR L210: I/O ERROR ON INPUT FILE
*** ERROR: PREMATURE END OF FILE ON 'Objects\TempFan'
```

**排查过程**
`selftest.c` 里 `st_msg()` 用了 `delay_ms()` 等发送完再继续，
但文件顶部那串 `#include` 里**没有 `delay.h`** ——
`timer.h / smg.h / motor.h / key.h / uart.h / indicator.h / ds18b20.h` 都包含了，
偏偏漏了 `delay.h`。

**根本原因**
C51 要求被调用的函数必须有 **ANSI 风格的函数原型**（`void f(void);`），
不能靠"隐式声明"蒙混过关。
`delay_ms` 的原型在 `delay.h` 里，没包含进来就只剩一个名字，
编译器无法确定参数类型，直接判为错误。

**为什么之前一直没暴露？**
因为 `SELFTEST_MODE = 0` 时，问题 21 那个 `#if` 把整个文件编译成了空 ——
**自检代码从来没被真正编译过，里面缺什么头文件自然也发现不了。**
这是一个典型的"两个 bug 互相掩盖"：问题 21 藏着问题 22。

**解决办法**
补上 `#include "delay.h"`。补完之后：

```
Program Size: data=93.0  xdata=175  code=7866     ← 0 错误
```

`code` 从 5905 涨到 7866，正好印证自检代码这次真的编进去了。
7866 距离 8KB（8192）只剩 **326 字节**，所以自检模式是"用完就关"的临时配置。

**经验总结**
**被条件编译关掉的代码，等于长期没被验证过的代码。**
凡是 `#if` 控制的模块，一定要至少完整编译一次，不能想当然。

### 这 4 个问题说明了什么

| # | 问题 | Python 静态检查能发现吗 | 真编译器能发现吗 |
|---|---|---|---|
| 19 | `data` 空间溢出 37 字节 | ❌ 完全看不到 | ✅ 链接期 L107 |
| 20 | `data` / `code` 指针混用 | ❌ 语法完全合法 | ✅ 编译期 C259 |
| 21 | `#if` 写在 `#include` 之前，功能静默失效 | ❌ 检查全通过 | ✅ 编译期 C322 |
| 22 | 缺头文件（被条件编译掩盖） | ⚠️ 部分能查 | ✅ 编译期 C267 |

**一句话**：能编译就一定要真编译。
静态检查和等价仿真能覆盖"逻辑对不对"，
但**覆盖不了"内存放不放得下、指针指向哪个空间、条件编译有没有真的生效"** ——
而这些恰恰是 8 位机上最容易翻车的地方。

## 补充 2：把显示从数码管换成 LCD1602 之后，又踩了 Flash 溢出的坑

### 问题 23：自检固件涨到 8628 字节，超过 8KB Flash 上限

**现象**
按要求把显示器件从板载 8 位数码管换成 **LCD1602 字符液晶**（4 位数据模式）之后，
正式固件编译正常：

```
Program Size: data=84.0  xdata=175  code=6362      ← 没问题，8192 还剩 1830 字节
```

但自检版一编就出问题：

```
Program Size: data=84.0  xdata=175  code=8628      ← 超出 8192 足足 436 字节！
```

**排查过程**
1. 先算账。LCD 驱动确实比数码管驱动大：数码管只要一张 10 字节的段码表加一个扫描函数；
   LCD 要做 4 位模式初始化（含手册规定的那串"强制同步"序列）、命令/数据分离、
   定点数格式化。实测增量：
   - 正式固件：5905 → 6362（+457）
   - 自检固件：7866 → 8628（+762）
2. 这 762 字节把自检版顶出了 8KB 边界。
3. 第一反应是"把自检程序的提示文字写短点"。那些字符串确实占了约 1150 字节，
   砍掉能省 500 左右 —— 但算下来还差一截，而且把有用的排查提示删掉很可惜。
4. 回去看 `main.c` 的结构，发现真正的问题在这里：

```c
#if SELFTEST_MODE
    selftest_run();          /* 自检流程，函数里是 while(1)，不会返回 */
#endif
    while (1) {
        app_task();          /* 自检模式下永远走不到这里 */
    }
```

**根本原因**
`app_task()` 在自检模式下**永远不会被执行**，但它仍然出现在 `main()` 里，
于是**链接器把整个 `app.c`（2000 多字节）一起链进去了**。

**8051 的链接器（BL51）不会剔除"被引用但运行不到"的代码 —— 它只认"有没有被引用"。**
（它会为这类代码报 `WARNING L16: UNCALLED SEGMENT`，但那条警告指的是
"没有被任何地方调用"，而不是"调用不到"。）

**解决办法**
把自检做成**独立的构建**：链接时**干脆不给 `app.obj`**，并用命令行宏打开自检开关。

① `config.h` 里把宏用 `#ifndef` 包起来，允许命令行覆盖：

```c
#ifndef SELFTEST_MODE
#define SELFTEST_MODE   0
#endif
```

② `main.c` 里两套逻辑彻底分开：

```c
#if SELFTEST_MODE
    selftest_run();          /* 自检版：不链接 app.c */
#else
    app_init();
    app_banner();
    while (1) { app_task(); }   /* 正式版 */
#endif
```

③ 新增 `tools\build_selftest.bat`，两个关键点：

```
C51.EXE main.c ... DEFINE(SELFTEST_MODE=1)      ← 命令行覆盖宏，不用改 config.h
BL51.EXE 主程序模块...  TO TempFan_Selftest      ← 对象列表里**没有 app.obj**
```

结果：

```
Program Size: data=95.0  xdata=96   code=5111      ← 自检固件，0 错误
Program Size: data=84.0  xdata=175  code=6362      ← 正式固件，0 错误
```

自检固件从 **8628 降到 5111**，一次省了 **3517 字节** —— 比预想的多得多，
因为 `app.c` 占用的 79 字节 `xdata` 也一起省掉了
（`xdata` 从 175 掉到 96）。

**经验总结**
**"被引用"不等于"会执行"。**
在 8 位机上，Flash 占用是按"链接进去的代码"算的，不是按"运行时会跑到的代码"算的。
用 `#if` 分叉主循环时，要让另一分支的函数**根本不参与链接**，
而不是仅仅"运行不到"。

**附带的一个好处**：自检模式改为命令行 `DEFINE()` 传入后，
**用户不需要再手改 `config.h` 里的宏**了 ——
这正好从根上消除了问题 21 那类"改了宏忘记改回来 / 宏没生效"的事故。

### 顺带一提：改用液晶还带来两个副作用

| 变化 | 原因 |
|---|---|
| **CPU 占用从约 18% 降到约 13%** | 数码管需要每 2ms 中断一次扫一位（8 位一轮 16ms）；LCD 自带控制芯片，写一次就自己保持显示，中断里那一路 2ms 时间片被整个删掉了 |
| **`data` 从 93 降到 84 字节** | 数码管的 8 字节显示缓冲 `g_disp[]` 和扫描索引不再需要 |
| **`xdata` 从 175 涨到 175（不变）** | `app.c` 的状态变量本来就都在 xdata；LCD 只需要 1 字节的列号 `s_col` |
